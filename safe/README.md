# Как пользоваться тремя промптами безопасного вайбкодинга

Комплект помогает поручить Codex или Claude Code проверку приложения, настройку Linux VPS и восстановление после аварии. Каждый промпт самостоятельный: его можно целиком вставить в отдельную задачу агента.

| Ситуация | Что использовать |
| --- | --- |
| Создаёте, дорабатываете или впервые проверяете приложение | [Промпт 1: защита приложения](master-prompt-1.md) |
| Хотите разместить приложение на Linux VPS или привести существующий сервер в порядок | [Промпт 2: настройка VPS](master-prompt-2.md) |
| Есть подозрение на взлом, утечка секрета, повреждение данных или серьёзная авария | [Аварийный промпт](incident-prompt.md) |

Первый промпт адаптируется к стеку и способу размещения, включая статические сайты. Второй предназначен для Linux VPS. Для управляемой платформы или serverless серверные пункты могут быть неприменимы: агент должен обозначить отдельный путь настройки платформы и подготовить требования, не навязывая VPS.

Цель первых двух промптов — полная автоматизация релизов, отката, мониторинга и уведомлений. После настройки обычные обновления выполняются через проверенные GitHub Actions или подходящие проверенные средства платформы. Повторять серверный промпт перед каждым выпуском не нужно. Выбранное подтверждение выпуска или ручной запуск workflow допускаются; сами операции затем выполняются автоматически.

## Как агент работает самостоятельно

Агент изучает факты, кратко объясняет план, выполняет работу в согласованных границах и проверяет результат. Он сам выбирает техническое решение, добавляет проверки и исправляет свои ошибки.

Специальных фраз подтверждения нет. Не нужно разрешать каждую команду или повторно согласовывать уже принятое решение.

Агент обращается к вам, когда:

* ему не хватает фактов, которые нельзя определить самостоятельно;
* возможны ещё не согласованные потеря данных, простой или потеря доступа;
* потребуются расходы;
* нужно существенно расширить задачу или доступ;
* предстоит необратимое действие с ещё не определёнными последствиями.

Он должен объяснить последствия и рекомендовать вариант. Можно ответить «не знаю» — тогда агент сначала уточнит факты или предложит осторожное решение, не выдавая неизвестное за безопасное.

Если хотите получить только план, прямо напишите об этом или используйте режим планирования. Тогда агент не приступает к реализации. Для полной работы обязательного переключения режимов интерфейса нет: нужны подходящие технические разрешения для текущего этапа. Системный запрос доступа может по-прежнему потребовать вашего действия; текст в чате не отменяет ограничения среды.

## Объём работы зависит от проекта

Агент сначала выясняет, какие данные и функции нужно защищать, что доступно публично, каковы последствия отказа и что уже работает. Для каждого нового сервиса, workflow или процесса он должен назвать конкретный пробел и способ проверки. Достаточный проверенный механизм сохраняется; дубликат ради чек-листа не создаётся.

Полная автоматизация остаётся целью, но отдельные функции можно объединять. Например, выпуск, откат и проверка сайта могут использовать существующий процесс платформы, если подтверждены все необходимые свойства и ограничения доступа. Отсутствие файла с примерным названием не является проблемой; отсутствие нужной проверки — является.

Security Watcher означает регулярный контроль уязвимостей. Агент сначала проверяет возможности существующих средств и добавляет только недостающее. Частоту, допустимые задержки и нагрузку он обосновывает риском проекта; общего требования проверять любой сайт каждые три часа нет.

## Субагенты

Для объёмной задачи основной агент может поручить отдельные части работы субагентам: например, изучение зависимостей или дополнительное ревью. Он сам распределяет задачи, проверяет выводы и собирает общий результат. При работе с VPS и инцидентом изменения одной системы выполняются последовательно под его управлением.

Субагенты необязательны и расходуют дополнительные токены и лимиты. Специально настраивать команду помощников не требуется: промпты предусматривают использование доступных возможностей Codex или Claude Code и последовательную работу с тем же охватом, если делегирование недоступно или не приносит пользы. Ревью другим агентом дополняет технические проверки.

## Что остаётся за вами

**Commit, push, merge и настройки GitHub выполняете вы.** Агент готовит файлы, проверяет их и даёт точные инструкции. При затруднении попросите объяснить следующий шаг простыми словами.

Также могут потребоваться действия, для которых у агента нет подходящего доступа: вход в кабинет провайдера, создание snapshot, настройка аккаунта, добавление секрета или проверка получения уведомления.

Просмотр плана и изменений помогает понять, что происходит. Он не заменяет техническую проверку и не требует от вас самостоятельно искать уязвимости — это часть работы агента.

## Перед использованием

Подготовьте:

* проект в Git-репозитории;
* аккаунт GitHub для публикации и включения автоматических проверок;
* Codex или Claude Code с доступом к папке проекта;
* сохранённую копию важных данных, если они уже есть.

Не отправляйте агенту пароли, приватные SSH-ключи, содержимое `.env`, токены и данные реальных пользователей. Когда секрет потребуется, агент должен объяснить, куда добавить его самостоятельно без публикации в чате или Git.

Работайте с ограничениями доступа под текущую задачу. Для первого промпта достаточно проекта и нужных официальных источников. Для второго потребуется доступ к указанному VPS. Для аварийного — к определённым затронутым системам и защищённому каталогу материалов расследования.

Если старое правило блокирует переход к следующему мастеру, агент должен назвать его и объяснить узкое изменение и возврат ограничений. Не требуется отключать всю защиту. Локальный режим только для чтения сам по себе не ограничивает возможности пользователя, подключённого по SSH к серверу.

# Промпт 1. Защита приложения

## Когда запускать

* Перед первой публикацией проекта.
* В существующем проекте, который ещё не проверяли.
* После значительных изменений авторизации, платежей, загрузки файлов или работы с данными.

## Как запускать

1. Откройте Codex или Claude Code в корневой папке проекта.
2. Вставьте [первый промпт](master-prompt-1.md). Если нужна реализация, предоставьте обычную ограниченную запись в проект.
3. Ответьте на необходимые вопросы. Агент изучит проект, изложит план и продолжит работу в согласованных границах.
4. После завершения прочитайте краткий результат: что исправлено, что проверено и что ещё не работает.
5. По инструкции агента самостоятельно сделайте commit и push.
6. По инструкции включите недостающие проверки и ограничения GitHub, добавьте нужные секреты выбранных каналов и выполните тестовые запуски. Уже работающие настройки агент проверяет без повторного создания.
7. Передайте результаты запусков агенту либо разрешите ему прочитать доступные результаты. Он должен сверить фактическое число PR и запусков с предварительной оценкой, проверить настройки обновлений и уточнить, какие механизмы проверены в работе.

## Что он подготовит

Агент проверит код и зависимости, исправит подтверждённые проблемы, добавит подходящие тесты и CI, подготовит регулярный контроль уязвимостей и инструкции для будущих AI-сессий. До публикации он должен объяснить ожидаемую нагрузку от первых и регулярных запусков GitHub, включая число предложений обновлений и проверок.

Применяются только нужные проекту механизмы. Статическому сайту без базы и сборки не требуется добавлять базу, серверный процесс или искусственную сборку ради чек-листа.

Требования к размещению и политика релизов сохраняются в контракте приложения, обычно `docs/production/APP_CONTRACT.md`. Существующий документ с теми же проверенными сведениями тоже подходит. Его расположение указывается в журнале: для Linux VPS он передаётся второму мастеру, для управляемой платформы описывает требования к её настройке.

Проверки должны отдельно показывать состояние репозитория и реально работающей версии. Исправление в GitHub ещё не означает, что пользователи уже получают исправленное приложение.

# Промпт 2. Настройка Linux VPS

## Когда запускать

После подготовки требований приложения, если:

* вы выбираете или впервые настраиваете собственный VPS;
* приложение уже работает на VPS, но его защита и эксплуатация не проверены;
* переезжаете на новый VPS или существенно меняете серверную архитектуру.

Если VPS ещё нет, агент сначала должен определить, нужен ли он приложению. Покупка сервера и связанные расходы требуют вашего решения.

## Как запускать

1. Откройте локальную папку проекта с результатами первого мастера или существующими требованиями приложения на своём компьютере. Если отдельного файла контракта нет, агент сначала проверит доступные сведения; повторять первый мастер только ради названия файла не нужно.
2. Вставьте [второй промпт](master-prompt-2.md).
3. Укажите состояние сервера: ещё не создан, пустой, тестовый, действующий или неизвестный.
4. Укажите SSH alias, IP или домен, а также пользователя и порт, если знаете их. Не отправляйте пароль или приватный ключ.
5. Агент проверит доступ и подлинность сервера, затем проведёт диагностику без намеренных изменений данных и настроек.
6. Ответьте на вопросы о важных данных, допустимом простое, резервных копиях и расходах. Уже согласованные действия повторно разрешать не нужно.
7. Агент подготовит и выполнит настройку в согласованных границах. Если нужно ваше действие в кабинете провайдера, он даст конкретную инструкцию.
8. Самостоятельно опубликуйте подготовленные файлы, настройте GitHub и запустите проверки по инструкции агента.
9. Проверьте итог: реальный deployment, выбранные уведомления, восстановление данных при их наличии и уровень проверки отката.

Если SSH ещё не настроен, агент должен пошагово объяснить создание отдельного ключа, установку его публичной части и проверку нового подключения. Приватный ключ остаётся в защищённом хранилище. Нельзя отключать единственный рабочий доступ до проверки нового.

## Что он сделает

По применимости агент защитит SSH и сеть, изолирует приложение, проверит HTTPS, закроет внутренние сервисы от публичного доступа, настроит резервные копии и проверку восстановления. Подготовит автоматические deployment, откат, страницу обслуживания и мониторинг.

Новый выпуск должен проходить такой путь:

```text
Изменения опубликованы пользователем в GitHub
→ CI и подготовка проверенного artifact
→ подтверждение или другая заранее выбранная политика выпуска
→ проверка новой версии по отдельному адресу
→ переключение публичного сайта
→ внешняя проверка сайта и фактической версии
→ успешный результат либо безопасный откат при совместимых данных
→ уведомление по выбранным каналам
```

Если откат небезопасен или не удался, требуется аварийный сценарий. Повторный deployment той же версии и предварительная проверка без переключения подтверждают только часть механизма отката. Агент должен явно отличать их от проверенного возврата между двумя различными совместимыми релизами.

# Аварийный промпт

## Когда запускать

* Есть признаки взлома, неизвестные ключи, пользователи, процессы или изменения сайта.
* Production мог использовать доступную из интернета критическую уязвимость.
* Раскрыт секрет или захвачен GitHub, домен, email либо аккаунт провайдера.
* Deployment сломал приложение, а обычный откат не помог.
* Повреждены данные, не восстанавливается backup или потерян доступ.
* Production недоступен, а причина неизвестна.

Это единственный полный аварийный сценарий комплекта. При признаках инцидента первые два мастера подготавливают передачу контекста в него.

## До запуска

По возможности сохраните текущее состояние: не очищайте логи, не удаляйте подозрительные файлы и не восстанавливайте резервную копию поверх production. Перезагрузка, выключение и хаотичная смена секретов могут уничтожить сведения или затруднить восстановление.

Если данные прямо сейчас уничтожаются или продолжается утечка, сообщите об этом первым. Ограничение ущерба может быть важнее полного сбора сведений.

Запускайте агента с доверенного компьютера. При подозрении на взлом локального устройства используйте другое доверенное устройство; не вводите новые секреты на подозрительном VPS.

## Как запускать

1. Откройте локальную папку проекта и вставьте [аварийный промпт](incident-prompt.md).
2. Опишите, что произошло, когда это заметили и какие действия уже выполнили.
3. Агент определит срочность, затронутые системы и ближайший безопасный шаг.
4. Выберите допустимые последствия, когда это необходимо: например, временно закрыть сайт или восстановить данные на выбранный момент. Агент должен объяснить вариант и его риск.
5. Агент выполняет согласованные этапы, проверяет результаты и сообщает о новых существенных обстоятельствах.

Специальных фраз нет. Общая просьба восстановить сайт не определяет допустимую потерю данных, стоимость нового VPS или разрешение удалить старую среду — такие решения должны быть конкретными.

При обычной операционной аварии агент исправляет её причину. Истёкший сертификат сам по себе не требует нового сервера, замены всех ключей или восстановления базы. При возможной компрометации необходимость чистой среды, ротации секретов и восстановления данных определяется отдельно.

После простой операционной аварии достаточно краткой записи причины, воздействия, исправления, проверки и предотвращения повторения. При возможной компрометации, утечке, повреждении данных, существенном или повторяющемся сбое нужен подробный разбор.

Материалы расследования с секретами и персональными данными хранятся вне репозитория в согласованном защищённом месте. В Git и отчёт попадают только очищенные сведения. При ситуации, требующей специалиста, агент должен назвать причину и подготовить передачу контекста.

# Как понять, что действительно работает

| Состояние | Значение |
| --- | --- |
| Подготовлено локально | Файлы и локально доступные проверки готовы; GitHub ещё может не выполнять их |
| Включено пользователем | Изменения опубликованы и настройки включены; это ещё не доказательство успешного запуска |
| Проверено в работе | Есть фактический результат запуска или доставки с датой и подтверждением |
| Не проверено / ошибка | Защиту пока нельзя считать работающей; указаны причина и следующий шаг |

У каждого требования также есть применимость: обязательное, обязательное при определённом условии, необязательное либо неприменимое с обоснованием. Отсутствие необязательного инструмента не должно блокировать результат, если необходимая защита обеспечена проверенным эквивалентом.

Агент отдельно оценивает безопасность в проверенных границах и готовность автоматизации. Непроверенный откат не считается работающим; отсутствие полной автоматизации само по себе не означает найденную уязвимость. Статус полной готовности к автоматическим релизам требует реальных проверок всех применимых функций.

В единой матрице агент сопоставляет требования с результатом: «требование → применимость → где реализовано → результат проверки → оставшийся пробел». Например, для группировки Dependabot он должен указать реальные правила в конфигурации и уровень их проверки, а не только написать «группировка настроена». Матрица хранится один раз; журнал и итоговый отчёт ссылаются на неё. Однородные проверки можно объединять, сохраняя отдельные результаты и пробелы.

Проверки блокируют изменения в GitHub только после настройки обязательных проверок и правил веток. Наличие workflow-файла само по себе этого не обеспечивает.

Возможности GitHub зависят от тарифа и публичности репозитория. Агент должен проверить доступность нужных функций. Если подтверждение deployment через GitHub Environment недоступно, он подготовит более слабый вариант с ручным запуском и проверкой точной версии, объяснит ограничения и не будет выдавать его за равнозначную защиту. Покупка тарифа не производится автоматически.

## Подключение GitHub и ошибки проверки

Сообщение «GitHub подключён» означает наличие подключения, но не доказывает доступ конкретной проверки к нужному API. Локальный инструмент и GitHub Actions могут работать с разными правами. Агент должен проверить нужный запрос именно там, где выполняется проверка, а работу ещё не включённого workflow отметить как непроверенную.

При ошибке `403`, `401`, `429` или недоступности сети агент выясняет причину, использует подходящий существующий доступ и при необходимости предлагает конкретное действие. Повторно подключать аккаунт или выдавать широкий токен наугад не нужно. Если источник временно недоступен, агент проверяет подходящую альтернативу и указывает точные границы результата: какие компоненты проверены и какие пока нет.

## Обновления зависимостей и нагрузка GitHub

По умолчанию совместимые обычные небольшие обновления объединяются в еженедельные PR. Начальный лимит — один открытый обычный PR на блок настроек Dependabot; в проекте с несколькими блоками PR может быть больше одного. Крупные переходы библиотек и платформ планируются отдельной задачей, без обычных автоматических major-PR и без автоматического слияния.

Исправления уязвимостей обрабатываются отдельно и своевременно. Лимит обычных PR не ограничивает security PR. Если исправление требует крупного перехода или текущая версия перестаёт поддерживаться, агент должен выделить задачу перехода и объяснить срочность.

Перед публикацией агент оценивает первую волну PR, число проверок и регулярные запуски. Это прогноз, а не гарантия количества jobs или расходов. После включения пользователем он сверяет прогноз с доступными результатами. Необходимые проверки проекта сохраняются; группировка и устранение повторных запусков должны снижать лишнюю нагрузку. Если остались заменённые обычные PR или ненужные запуски, агент проверяет, что нужные security-обновления сохраняются, и даёт вам точный список действий по их закрытию или отмене.

## Уведомления и работоспособность проверок

Выберите Telegram + email + GitHub, email + GitHub либо только GitHub. Telegram необязателен; проверяются выбранные каналы. Агент должен объяснить, если выбранный способ требует более внимательного ручного наблюдения.

Регулярное сообщение от проверки уязвимостей не гарантирует обнаружения её полной остановки. Для этого нужен независимый наблюдатель за временем последнего успеха всех необходимых средств контроля; доступность сайта не заменяет эту проверку. Агент сначала использует подходящий существующий внешний мониторинг; если его нет, предложит настройку и честно обозначит ограничение до проверки.

Расписания GitHub могут задерживаться, пропускаться или отключаться. Пока независимый контроль не настроен, агент должен дать понятную процедуру ручной проверки, а не обещать автоматическое уведомление при любом отказе.

## Если проблему пока нельзя устранить

Временное исключение не должно становиться бессрочным. Для принятого риска безопасности, временной защиты вместо исправления или сохраняющегося подавления security-предупреждения агент ведёт `docs/security/EXCEPTIONS.md`: достаточно одной компактной записи на исключение. Обычные замечания оформления кода туда не входят. Подтверждённое ложное срабатывание агент проверяет самостоятельно; без постоянного подавления достаточно результата проверки, без отдельного реестра и вашего согласования.

В записи указываются причина и доказательства, затронутая система и версия, защитные меры, ответственный, следующий шаг, срок действия и конкретная дата пересмотра. Агент не принимает риск за вас; уже согласованные неизменившиеся последствия повторно разрешать не нужно.

Наступление даты пересмотра, истечение срока, изменение затронутой версии или условий, появление исправления либо сведений об эксплуатации возвращают исключение на проверку. Автоматического продления нет. Принятый риск остаётся видимым и не отменяет обязательные условия готовности.

Контроль сроков включается в существующие регулярные проверки; отдельный Watcher только ради реестра не нужен. Пока он не проверен в работе, агент указывает ручной порядок и ответственного; обещать автоматическое напоминание нельзя. При передаче следующему мастеру реестр сохраняется вместе с журналом.

## Где сохраняются результаты

Для нового проекта агент группирует сведения в security baseline, контракте приложения, контракте сервера при наличии VPS и журнале прогресса. Политика релизов, инструкции эксплуатации и передача контекста могут быть разделами этих документов. Пригодную существующую структуру он сохраняет; отдельные файлы из примеров создавать необязательно.

В журнале есть карта «сведения → документ/раздел». Следующий мастер читает её, затем проверяет прежние стандартные пути и фактическое состояние. Недостаток важных фактов останавливает зависимый шаг; отсутствие конкретного имени файла — нет. Секреты и необработанные материалы расследования в эти документы не попадают.

## Если работа прервалась

После начала изменений агент ведёт `docs/safe/PROGRESS.md`: цель, границы, этапы, результаты проверок, карта документов, ссылка на единую матрицу и исключения, ожидаемые действия пользователя и следующий шаг.

При продолжении передайте тот же промпт и укажите журнал. Агент должен сверить записи с реальным состоянием проекта и сервера. Уже выполненные миграции, ротации и переключения нельзя повторять вслепую. В режиме только планирования состояние передаётся в ответе без записи файлов.

## Выбор следующего действия

| Событие | Следующий шаг |
| --- | --- |
| Важное изменение приложения | Промпт 1 |
| Настройка или переезд Linux VPS | Промпт 2 |
| Обычное обновление кода или зависимостей без признаков инцидента | Проверенный GitHub Actions deployment |
| Исправление уже в основной ветке, но deployment не состоялся | Считать production отдельно; проверить реально работающую версию |
| Возможная эксплуатация критической уязвимости, утечка секрета или взлом | Аварийный промпт |
| Deployment не удался, безопасный откат сработал | Изучить ошибку и подготовить исправление |
| Откат не помог или могли пострадать данные | Аварийный промпт |

Промпты помогают установить и проверить защиту в определённых границах. Итог должен содержать конкретные результаты и непроверенные области; факт выполнения промпта не является гарантией отсутствия уязвимостей или взлома.
